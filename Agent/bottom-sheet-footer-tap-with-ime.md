# Android `BottomSheet`: a `Footer` button must fire on the first tap while the IME is up

## Goal

On Android, with a `TextInput` focused inside `BottomSheet.Body` and the keyboard showing, a single tap on a button in `BottomSheet.Footer` fires its `onPress`. Today (PR #102 device pass, Pixel_10 AVD, template debug build, `@expo/ui` 58.0.2, `expo-modules-core` 58.0.2, RN 0.88.0-rc.0) the tap dismisses the keyboard and `onPress` does not run; a second tap works (2 of 2 trials). Find which layer swallows the press with instrumentation on device, fix it in the package where the package owns it, keep iOS and web unchanged, add tests, CHANGELOG (`## [0.27.1]`, unreleased) and docs. No version bump.

## Context

Verified on `dev` at 273f198.

- **Sheet content lives in another native window but in the same React tree.** `@expo/ui`'s Android sheet (`node_modules/@expo/ui/src/community/bottom-sheet/BottomSheet.android.tsx:216-227`) renders `Host > ModalBottomSheet > RNHostView > View{flexGrow:1,height:0} > SheetScrollContextReset > children`. `RNHostView.kt` (`node_modules/@expo/ui/android/src/main/java/expo/modules/ui/RNHostView.kt`) hosts our column in a `TouchDispatchingRootViewGroup` inside the Material dialog window and streams its touches to JS through its own `JSTouchDispatcher` (`dispatchesTouchesToJS` true for a layout root). It also relays Compose `ACTION_CANCEL` and `onChildStartedNativeGesture` to JS. The React responder negotiation (`ResponderEventPlugin`) walks the **fiber** tree, so every React ancestor of `<BottomSheet>` on the consumer's screen takes part in the capture phase for taps inside the sheet even though none of them is under the finger.
- **RN `ScrollView` tap-to-dismiss.** `node_modules/react-native/Libraries/Components/ScrollView/ScrollView.js:1570-1647`: with `keyboardShouldPersistTaps` unset or `"never"`, an ancestor `ScrollView` returns `true` from `onStartShouldSetResponderCapture` when `TextInputState.currentlyFocusedInput()` is a registered input and `_keyboardMetrics != null` (set by RN `Keyboard` `keyboardDidShow`, which on Android comes from the activity root's `isVisible(ime())`, `ReactRootView.java:935-964`), and the target is not a text input. It then owns the touch, no descendant is ever asked (`executeDispatchesInOrderStopAtTrue` runs capture listeners root→target first), and on release it calls `TextInputState.blurTextInput(currentlyFocusedInput)` (`:1475-1481`). `@expo/ui` registers each hosted field's `Host` view with `TextInputState` and routes `blurTextInput` to the field (`node_modules/@expo/ui/src/keyboard/index.tsx`, `interop.ts`), so that blur does hide the keyboard. `Body` already sets `keyboardShouldPersistTaps="always"` (`packages/ui/src/components/BottomSheet.tsx:843`) for its own ScrollView; `Footer` is outside `Body`. The #102 lab route (`/tmp/sheet-ime-lab.tsx`) rendered its three sheets inside a plain `ScrollView` with the default `keyboardShouldPersistTaps`, i.e. exactly this configuration. The showcase screen uses `KeyboardAwareScrollView keyboardShouldPersistTaps="always"` (`client/showcase/ShowcaseScreen.tsx:131-133`); the package `DismissKeyboard` uses `always` too.
- **Package tap-away boundary.** `BottomSheetContent` spreads `useKeyboardDismissResponder()` on the column (`BottomSheet.tsx:670`, `keyboardDismiss.ts:226-273`). Its `onStartShouldSetResponder` runs only in the bubble phase when no descendant claimed; it always returns `false`, arms a pending tap and dismisses on `onTouchEnd` via the `keyboardFocusRegistry` blur handle. A `Pressable` (`Button`, `Button.tsx:351-360`, `focusable` default, `hitSlop` from `getNativeHitSlop`) claims on start, so a normal Footer tap never reaches the boundary's arm.
- **Other candidates from #102.** `Pressable` cancel: `Pressability` fires `onPress` on `onResponderRelease` only while the press is inside the responder region measured at grant; a native `ACTION_CANCEL` (Compose consuming the pointer, `onChildStartedNativeGesture`) terminates it. Focus steal: a View that is focusable-in-touch-mode takes View focus from the field's `ComposeView` on touch and the IME hides (the 0.27.0 `StyledText selectable` case); `Button` already forces `TextSelectabilityContext=false`. IME hide reasons are visible in `adb logcat -s ImeTracker` (`onRequestHide … reason …`).
- **Harness.** `android/` and `ios/` are gitignored; `.env` is gitignored and must be exported before Gradle or the debug APK lacks the expo-updates fingerprint asset and crashes on launch (#102 note). Private AVD copies of `Pixel_10` (API 36, 1080×2400) exist (`Pixel_10_sheetime`); make a new unique copy. `client/showcase/details.tsx:206-238` has Body-only sheets; a temporary uncommitted lab route under `app/(main)/(demos)/` is the harness, as in #97 and #102.

**Decision (night mode).** Diagnose first; the fix follows the layer:

- (A) If an ancestor `ScrollView` claims the tap in the capture phase, the package cannot preempt it from inside the tree (capture runs root-down; a React portal keeps the fiber chain; a host-based portal would drop consumer context and is a breaking change). Deliverable: a precise, evidence-based dev warning from `BottomSheet.Content` when it observes a swallowed tap while a sheet field is focused, plus docs telling consumers to set `keyboardShouldPersistTaps="always"` (or `"handled"`) on ancestor scroll views or use `DismissKeyboard`, plus device proof that the first tap fires once the ancestor is fixed. Do not fork `@expo/ui`, do not portal, do not touch `TextInputState`.
- (B) If the press is cancelled or missed after a focus/IME change caused by something the package renders (a focusable-in-touch-mode view in `Footer`/`Button`, the boundary arming when it should not, a Pressable region miss), fix that in the package on Android only (platform-gated), with a unit test that reproduces the sequence.
- (C) If a native layer outside the package cancels the press (Compose interop `ACTION_CANCEL`, `RNHostView`), record the exact evidence in the PR, add the dev warning from (A) if it also applies, file the upstream pointer in the PR body, and ship docs + CHANGELOG describing the limitation. Do not add JS workarounds that fire `onPress` from touch events.

## Work

1. **Lab + instrumentation (temporary, uncommitted).** `app/(main)/(demos)/sheet-footer-tap-lab.tsx` with two variants side by side, each a 60% sheet with `Handle` + `Header` + `Body` (`TextInput` ×2) + `Footer` `Button` whose `onPress` increments a visible counter (`testID` on the counter text and the button): variant S wraps its trigger in a plain `ScrollView` (default `keyboardShouldPersistTaps`); variant V wraps it in a plain `View`. Instrument with `console.log` tagged `[footer-tap]`: in `keyboardDismiss.ts` `useKeyboardDismissResponder` (start-should-set asked / armed / dismiss fired), on the lab column via `BottomSheet.Content` props `onStartShouldSetResponderCapture` (capture reached), `onTouchStart`/`onTouchEnd`/`onTouchCancel`; on the lab button `onPressIn`/`onPressOut`/`onPress`; on the lab `TextInput` `onFocus`/`onBlur`; a `Keyboard.addListener("keyboardDidShow"/"keyboardDidHide")` logger in the lab. Read the logs from Metro. Also capture `adb logcat -s ImeTracker:* InputMethodManager:*` around one tap per variant.
2. **Classify.** For each variant, focus the first field, wait for the IME, tap the Footer button once (argent tap at the button frame's centre), record: counter value, which logs fired and in which order, the `ImeTracker` hide reason. Rule: capture-not-reached + no boundary arm + counter unchanged ⇒ (A) for that variant. Boundary armed and dismiss fired ⇒ (B, boundary). `onPressIn` fired, `onPress` not, `onBlur` between them ⇒ (B or C, cancel/miss) — then `adb shell dumpsys activity top | grep -A2 'mFocused'` right after the tap and the `ImeTracker` reason decide whether a package view took focus (B) or a native cancel arrived (C: `onTouchCancel` on the column). Repeat 3 taps per variant; report counts.
3. **Fix.**
   - (A): `packages/ui/src/components/BottomSheet.tsx` `BottomSheetContent`: Android + `__DEV__` only, once per session, warn when a touch starts on the column (`onTouchStart`) while `hasKeyboardFocusedInput()` is true and the column's `onStartShouldSetResponderCapture` was not invoked for that same event (same `identifier`+`timestamp`, i.e. an ancestor claimed it in the capture phase). Message names the cause and the remedy: `@mrmeg/expo-ui BottomSheet: an ancestor ScrollView claimed a tap inside the sheet while a sheet field was focused (React Native's keyboardShouldPersistTaps="never" default), so the tapped control did not fire. Set keyboardShouldPersistTaps="always" or "handled" on scroll views that contain the BottomSheet, or wrap the screen in DismissKeyboard.` Implement the tracking in `keyboardDismiss.ts` next to `useKeyboardDismissResponder` (export a small `useSwallowedTapWarning`-style hook or extend the returned props; keep the boundary's own behavior unchanged) so it is unit-testable. iOS keeps the same check only if the iOS lab shows the same swallow; otherwise gate to Android and say why. Web: no-op.
   - (B): the minimal Android-gated change at the offending view/handler; keep iOS/web code paths byte-identical in behavior.
   - (C): docs + CHANGELOG + PR evidence only, per the decision.
4. **Tests** (`packages/ui/src/components/__tests__/`): `keyboardDismiss.test.tsx` / `BottomSheet.test.tsx` cases for whatever shipped: for (A) a rendered `<BottomSheet open>` column with a registered focused input where `onTouchStart` arrives without a preceding capture call warns once (message contains `keyboardShouldPersistTaps`), a touch that did go through capture does not warn, iOS/web do not warn (unless iOS is included), and the warning does not fire when no field is focused. For (B) a test that reproduces the swallowed sequence on Android and asserts `onPress` fires. Existing 43+ sheet tests stay green.
5. **Docs.** `packages/ui/README.md` BottomSheet section and `packages/ui/LLM_USAGE.md`: state that sheet content takes part in the screen's responder tree, that an ancestor `ScrollView` with the default `keyboardShouldPersistTaps` swallows the first tap on sheet controls while a sheet field is focused, and the remedy (`always`/`handled`, or `DismissKeyboard`). Run `bun run docs:llms`; commit regenerated `llms*` files if they change. `packages/ui/CHANGELOG.md` `## [0.27.1]` → `### Fixed`: one entry describing the found layer, the change, and that iOS/web are unchanged. Do not bump `packages/ui/package.json`.
6. **Device evidence in the PR body** (argent frames normalized to the screen; screenshots stay out of the repo): before/after counters per variant, the log order per class, `ImeTracker` reason, AVD name, build versions. Record the iOS observation: if the slot and load allow within the session, run the same lab on an iOS simulator with a template debug build and state whether the first tap fires; otherwise state that iOS was not run and why, and rely on the tests' platform gating.
